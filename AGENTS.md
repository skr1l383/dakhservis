# Правила проєкту «ДахСервіс»

Цей файл читає агент перед кожною задачею. Правила обов'язкові.

## Головне правило

Спека є джерелом правди. Якщо задача, план або прохання в чаті суперечить
`specs/001-inspection-requests/spec.md`, зупинись і запитай. Не вгадуй і не
заповнюй прогалини власними припущеннями: якщо чогось немає у спеці, додай
питання в розділ «Відкриті питання» і чекай на відповідь.

## Порядок роботи

1. Код пишеться лише після того, як замовник погодив спеку (коментар
   «Погоджено» в PR зі `spec.md`).
2. Працюй лише над однією задачею з `tasks.md` за раз.
3. Для кожної задачі: спершу тест із критерію приймання, потім реалізація.
4. Якщо під час реалізації виявилося, що спека чи план неправильні, спершу
   змінюється документ, потім код.
5. Зміна вимог іде в такому порядку: питання замовнику → спека → план →
   задачі → тести → код. Кожна зміна записується в «Журнал змін» спеки.

## Стек

- Мова: TypeScript (strict)
- Сервер: Node.js, Express
- База даних: SQLite
- Тести: Vitest, для API додатково supertest
- Інтерфейс: прості HTML-сторінки без фронтенд-фреймворку

## Структура папок

```
specs/001-inspection-requests/
  spec.md      що і навіщо будуємо, критерії приймання
  plan.md      як будуємо: модель даних, статуси, API
  tasks.md     список задач із посиланнями на AC
  adr/         записи про архітектурні рішення
src/           серверний код
public/        сторінки інтерфейсу
tests/         тести
AGENTS.md      цей файл
```

## Тестування

- Кожен тест посилається на критерій приймання у назві,
  наприклад: `AC-1.2: дата в минулому → 400 з полем date`.
- Кожен AC зі спеки має щонайменше один тест.
- Задача вважається виконаною лише тоді, коли проходять її тести і всі
  попередні.
- Заборонено видаляти, пропускати (`skip`) чи послаблювати тести, щоб вони
  проходили. Якщо тест здається неправильним, зупинись і запитай.

## Доступи ролей

Права клієнта, диспетчера й інспектора перевіряються на сервері в кожному
маршруті. Приховати кнопку в інтерфейсі недостатньо.

## Заборони

- Не додавати залежності без погодження.
- Не змінювати файли поза поточною задачею.
- Не писати код, який не закриває жодного AC.
- Не змінювати `spec.md` самостійно: тільки пропонувати зміни.
- Не додавати у спеку технології: у ній лише поведінка, яку може
  перевірити замовник.

## Коміти

- Один коміт на одну задачу, номер задачі на початку повідомлення:
  `T-03: створення заявки через API (AC-1.1, AC-1.2)`.
- Зміни документів і зміни коду йдуть окремими комітами: документ першим.
